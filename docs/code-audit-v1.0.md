# Yuanshen v1.0 全代码风险审查

## 审查范围与结论

审查日期：2026-07-26。

本次检查覆盖 `yuanshen.py` 的任务规范化、System/User Prompt、Todo 状态机、本地工具、
MCP 调度、音频验收、Agent 循环、终端输入和任务归档，同时检查
`esp32_piano_mcp.py`、npm 启动器、包元数据及现有说明文档。基础语法编译和 npm
打包检查通过，但发现以下 10 项可能影响安全性、完成判定或稳定性的风险。

这些问题不代表每项都曾在当前环境复现。正式版 1.0 后续修订已按本文方案完成代码
整改；目前均标记为“已修复，等待更长时间的实机回归”。涉及 ESP32 和麦克风的判定仍
需在不同硬件、串口和录音环境中持续验证。

## 1. Shell 黑名单可被变体绕过（高）

**检查位置：** `run_bash()`、`BANNED_CMDS`。

程序使用 `shell=True` 执行模型给出的整段命令，只通过少量区分大小写的子字符串阻止
危险命令。额外空格、绝对路径、大小写、变量展开、编码或间接脚本都可能绕过检查；
复合命令还可能把安全命令与危险操作串在一起。

**解决方案：** 默认改为参数数组并关闭 shell；建立允许的命令和参数白名单。确需 shell
语法时放入隔离执行器，解析 AST 后逐命令校验，并限制环境变量、工作目录和执行时限。

**修复状态：** 已关闭 `shell=True`，使用 `shlex` 拆分、命令白名单并拒绝 shell 元字符。

## 2. MCP 本地路径未统一经过目录边界校验（高）

**检查位置：** `task_file()`、`execute_tool()` 中 MCP 的 `out_path`、`local_path`、
`path` 转换。

本地读写工具会经过 `safe_path()`，但传给 MCP 的绝对路径或带斜杠路径只经过
`task_file()`，没有强制位于当前任务目录或工作目录。模型参数可能让录音或上传读取到
任务范围外的文件。

**解决方案：** 为 MCP 参数增加专用 `safe_task_path()`；写入路径必须位于
`CURRENT_TASK_DIR`，允许读取的工程文件建立显式只读根目录；在调用 MCP 前对解析后的
绝对路径再次验证。

**修复状态：** 已增加 `safe_mcp_path()`，覆盖上传、录音、分析和对比文件参数。

## 3. 实机验证证据判定过宽（高）

**检查位置：** `TodoManager.observe_tool()`。

只要当前任务曾成功上传 `main.py`，之后任意成功的 `repl_exec`、`run_script` 或
`play_and_record` 都会把 `device_verified` 设为真。调用可能只是 `print("pong")`、
执行其他脚本或触发单独蜂鸣命令，并不证明板上的当前 `main.py` 完整运行正确。

**解决方案：** 给烧录内容计算哈希；验证工具必须明确执行板上 `main.py`，并返回启动
标记、需求断言和同一哈希。只有证据对象同时匹配当前部署版本与验收项时才放行测试。

**修复状态：** 已记录上传文件 SHA-256，代码改变即失效；验证只接受明确打开并执行
板上 `main.py` 的 `repl_exec` 或 `play_and_record`。

## 4. `AudioSkipped` 被轮次统计为工具成功（中高）

**检查位置：** `execute_tool()` 与 `agent_loop()` 的 `ok` 计算。

音频关闭或自动降级后返回 `AudioSkipped: ...`，而循环只把 `Error` 和
`Unknown tool` 前缀视为失败，因此状态行会显示该麦克风工具“成功”。虽然 Todo 的音频
策略允许降级，但审计语义会把“未执行”误记为“成功”。

**解决方案：** 工具结果改为结构化状态 `success|failed|skipped`；状态行和归档单独显示
“跳过”，且跳过不能作为音频证据。

**修复状态：** 已实现三态结果，屏幕和归档不再把 `AudioSkipped` 记为成功。

## 5. 音频任务识别依赖有限关键词（中高）

**检查位置：** `TodoManager.requires_audio_validation()`。

是否启动音频验收只检查“蜂鸣器、喇叭、声音、发声、音频、音乐”。“警笛、提示音、
扬声器、speaker、beep、horn”等任务可能漏判；反之，需求中写“不要发出声音”也可能
误判为必须验收。

**解决方案：** 在循环外规范化结果中输出明确布尔字段和验收类型，例如
`audio_validation.required`、`target`、`metric`；程序读取结构化字段，不再猜关键词。

**修复状态：** 规范化 JSON 已增加强类型 `audio_required`，Todo 不再扫描关键词。

## 6. 音频指标解析依赖中文展示文本（中高）

**检查位置：** `observe_tool()` 中对 `mic_check`、`analyze_wav` 输出的正则表达式。

噪声 RMS、峰值和音分偏差从自然语言文本中提取。工具措辞、空格、单位或小数格式稍有
变化就会得到 `None`，还可能把错误文本中的数字当成结果。

**解决方案：** MCP 音频工具返回带 schema 的 JSON 数据；程序校验数值类型、范围、
采样率、目标频率和文件身份，展示文本只用于用户阅读。

**修复状态：** `mic_check` 和 `analyze_wav` 已附加稳定的 `METRICS_JSON`，主程序优先
解析结构化指标。

## 7. MCP 请求超时使用墙上时钟（中）

**检查位置：** `MCPClient._request()`。

任务总时长已使用 `time.monotonic()`，但 MCP 超时仍用 `time.time()`。系统时间被 NTP
或人工向前/向后调整时，等待可能过早超时或显著超过设定时长。

**解决方案：** 截止时间和剩余时间全部改用 `time.monotonic()`，并在超时后终止或重启
失去响应的 MCP 子进程。

**修复状态：** MCP 请求截止时间已改用 `time.monotonic()`。

## 8. MCP 子进程错误输出被永久丢弃（中）

**检查位置：** `MCPClient.__init__()`。

MCP 服务以 `stderr=subprocess.DEVNULL` 启动。串口权限、依赖缺失、音频设备错误或服务
崩溃的关键诊断信息无法进入日志，用户只能看到“服务器已退出”或超时。

**解决方案：** 用独立线程读取有上限的 stderr 环形缓冲区；启动失败和调用异常时附上
最近若干行，并在任务归档中保存脱敏后的诊断信息。

**修复状态：** 已增加独立 stderr 读取线程和 50 行上限缓冲，超时/退出时附带近期诊断。

## 9. MCP 消息队列会丢弃非当前请求消息（中）

**检查位置：** `MCPClient._request()`。

等待某个请求 ID 时，其他 ID 的响应和通知会直接 `continue` 后丢弃。当前实现通常串行，
但一旦服务主动通知、未来并发调用或超时响应晚到，后续请求可能收不到原本属于自己的
响应，导致难以复现的超时。

**解决方案：** 建立按 request ID 分发的 pending map；通知走独立处理通道，未知响应
暂存或记录，避免消费后丢弃。

**修复状态：** 已增加 pending map，非当前响应按 ID 暂存，通知不再干扰请求响应。

## 10. Todo 状态允许回退，证据与状态缺少事务一致性（中）

**检查位置：** `TodoManager.update()`、工具执行后的 `observe_tool()`。

状态机检查顺序和完成门禁，但没有禁止 `completed → pending` 或跨轮反复切换。
此外工具副作用、证据字段更新和 Todo 更新分属不同调用：上传成功后如果模型未及时更新
Todo，或后续失败发生在两次调用之间，屏幕状态、Todo 与真实设备状态可能短暂不一致。

**解决方案：** 定义单向状态转换；把部署哈希、验证证据和 Todo 变更写入一个事件日志，
由程序根据事件派生状态。设备变化时自动失效关联步骤，并在下一轮明确输出失效原因。

**修复状态：** 已禁止 Todo 状态回退，增加部署哈希和证据日志，代码变化会自动失效旧
部署与验证结果。

## 建议处理顺序

1. 首先处理 1–4，避免越界执行和错误的完成/成功陈述。
2. 随后处理 5–6，建立结构化音频任务和音频证据。
3. 再处理 7–9，提高 MCP 的超时、诊断与消息分发可靠性。
4. 最后处理 10，并为整个 Todo/证据状态机补充回归测试。

每项修复都应至少覆盖：正常路径、失败路径、超时路径、状态失效路径和历史任务回放；
涉及 ESP32 或麦克风的项目还需完成真实设备 A/B 测试后再标记关闭。
